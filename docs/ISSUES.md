# 未解決の設計課題

実装しながら出てきた論点。優先度は「これが未解決のまま本番に出せるか」で付けています。

---

## P0 — 本番投入前に必須

### ブラウザ側のパスキー ceremony が未実装

サーバー側の検証（`Accounts.WebAuthn`）とリスク評価（`Accounts.Risk`）は実装済みでテストもあります。
足りないのは `navigator.credentials.create()` / `.get()` を呼ぶ JS と、
チャレンジの発行・保管・期限管理です。

現状の `/dev/session/:handle` は `:dev_routes` が真のときだけコンパイルされる開発用の抜け道で、
本番リリースには存在しません。これが埋まるまで、認証は「動くが使えない」状態です。

### 監査ログの追記専用化がアプリケーション層の約束でしかない

`audit_logs` は追記専用の想定ですが、現状は規約にすぎません。
本番では、アプリケーションが使うロールから `UPDATE` / `DELETE` を剥奪する必要があります。

```sql
REVOKE UPDATE, DELETE ON audit_logs FROM nerd_meet_app;
```

これをマイグレーションに入れるか、インフラ側の責務にするかは決めていません。
マイグレーションに入れると、ロール名がスキーマに埋まります。

### k-匿名化の初期運用パラメータ

`mix nerd.demo` で確認できるとおり、数百人規模では詳細バンドがほとんど成立しません。
コード上の階梯は正しく動きますが、**サービス開始直後にどのバンドから始めるか**は運用判断です。

現在の階梯は都道府県 → 地方 → 全国ですが、初期は地方ブロックと10年帯から始め、
人口が閾値を超えた地域から順に細かくしていく「適応的バンド化」を運用ポリシーとして定める必要があります。
この判断はコードではなく、公開ドキュメントに書かれるべきものです。

### 本人確認プロバイダの実装がモック

`IdentityProvider.Mock` は渡された値を信用します。
JPKI の実接続（署名検証、失効確認、CRL/OCSP）は未実装です。
behaviour と、トランザクション外で呼ぶ呼び出し規約だけが用意されています。

### VAULT_MASTER_KEY のローテーション手順がない

鍵を変えると既存の `wrapped_key` がすべて開けなくなります。
再包装（旧鍵で unwrap → 新鍵で wrap）のオンラインジョブが必要です。
現状では鍵を変えることが全会話の破棄と同義です。

## P1 — 早めに解決したい

### 段2の類似度計算が O(n²)

`Signals.template_ratio/1` は直近40件の全ペアを比較します。サンプル上限があるので現状は問題ありませんが、
上限を上げるならロケール感度ハッシュのバケット化が必要です。

### SimHash の閾値が短文で不安定

実測で、言い換えた文が距離14、無関係な文が27。閾値16はその中間に置いてあります。
短いメッセージほど指紋が荒くなるため、文長で閾値を可変にするか、シングルサイズを調整する余地があります。

### ブロックがマッチを閉じるが会話鍵は残る

`Social.block/3` はマッチを `closed_at` にしますが、会話鍵は破棄しません。
「ブロックしたら過去のやり取りも読めなくする」べきかは、
片方の意思でもう片方の記録を消してよいかという問題で、まだ決めていません。

### 通報からの自動連鎖がない

`report_count/1` は段2のシグナルとして使われますが、通報そのものはレビューキューに入りません。
通報が一定数を超えたら即座にレビュー対象にするジョブが必要です。

### `handle` の一意制約が大文字小文字を changeset に依存している

`User.registration_changeset/2` が `String.downcase` してから保存するので実質一意ですが、
データベース側は素の unique index です。`citext` か関数インデックスにすべきです。

## P2 — 議論が必要

### 相互条件マッチの計算量

`Members.mutual_query_matches/2` は公開クエリを全件取得してメモリ上で突合します。
公開クエリが数千件を超えると成立しません。

条件を正規化してインデックス可能な形に落とすか（範囲条件と集合条件だけに制限する）、
定期ジョブで事前計算するかの選択になります。前者は表現力を、後者は鮮度を犠牲にします。

### 「クエリ公開」の匿名性への影響

十分に具体的な条件は、それ自体が書いた人を特定しうる情報です。
「経験15年以上・Erlang・鳥取県」という公開条件は、書いた人の人物像をかなり狭めます。
公開クエリにも k-匿名化的な制約が要るのか、それとも本人が明示的に公開したものだから自由なのか。

### 段3にモデルを繋いだときのプライバシー開示

`Classifier` にモデルを設定すると、メッセージ本文が第三者に渡ります。
これは重大な方針変更なので、設定されている場合に UI 上で明示する仕組みが要ります。
設定値を読んでフッターに表示する程度でも、何もないよりはるかに良い。

### 年齢に関するパターンの誤検知

`@minor_claim` は「高1です」を捕まえますが、成人が過去を回想する文脈も巻き込む可能性があります。
現在は `(中|高)[1-3](年|生|です)` まで絞って「集中3時間」を除外していますが、
このトレードオフの置き場所は議論の余地があります。

### スナップショットの更新頻度

現在は手動または Oban ジョブでの再生成です。
頻繁すぎると差分から個人の出入りが推測でき、稀すぎると使えません。
差分攻撃への耐性を考えると、更新粒度そのものが匿名化パラメータです。
